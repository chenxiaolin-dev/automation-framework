# 通用智能测试平台方案

> 版本：v2.0（工程结构升级版） · 技术栈：Python 3.12 / pytest / httpx / PyYAML / Loguru / Allure / Faker / jsonschema（可选 Playwright / Appium / Minium / pymysql）

> **v2.0 结构升级说明**：工程重构为「统一底座 core/ + 分方向引擎 engines/ + 多项目用例隔离 projects/」三层。
> 底座新增：RuntimeContext 运行上下文、`${ENV.KEY}` 配置替换、outputs 分 run 目录规划、
> run.log + case log 双层日志与脱敏、Allure 元数据（environment.properties/executor.json）、
> 失败自动归因附件、生产环境保护（--allow-prod 双开关）。
> API 引擎升级为 YAML 用例驱动（变量四来源 / data_matrix 笛卡尔积 / depends_on 拓扑排序 /
> 20 种断言 / setup-teardown 动作 / jsonschema 校验），并新增统一运行入口 scripts/run.py。
> 详见 README.md 与 docs/用例编写规范.md。

## 一、背景与目标

测试团队同时服务于多个被测项目（项目A、项目B……），测试方向覆盖 **接口、Web UI、APP、微信小程序**。目标：

1. **一套框架，多项目复用**：以被测项目为隔离单元，新项目接入不改框架代码；
2. **配置与代码分离**：多环境（test / prod / 自定义）一键切换，CI 中环境变量可覆盖；
3. **数据与用例分离**：YAML 数据驱动，用例只写「取数 → 调用 → 断言」；
4. **公共能力下沉**：登录态、公共 Header、断言、日志、报告、失败重试统一封装，业务测试只写业务。

## 二、总体架构

```
┌─────────────────────────────────────────────────────────────┐
│  用例层  testcases/{api, ui, app, miniprogram}/              │  ← 只做取数、调用、断言
├─────────────────────────────────────────────────────────────┤
│  业务层  api/user_api.py · ui/pages/ · app/pages/ · mp/pages/ │  ← 接口/页面封装（Allure步骤）
├─────────────────────────────────────────────────────────────┤
│  请求/驱动层  HttpClient(httpx) · Playwright · Appium · Minium │  ← core/ 下统一封装
├─────────────────────────────────────────────────────────────┤
│  公共能力层  配置加载 · 登录态 · 断言工具 · 日志(Loguru) ·        │
│             报告(Allure) · 数据驱动(YAML) · 失败重试 · Faker造数 │
├─────────────────────────────────────────────────────────────┤
│  配置/数据层  projects/<项目>/config/env_<env>.yaml            │
│              projects/<项目>/config/accounts.yaml             │
│              projects/<项目>/data/*.yaml                      │
└─────────────────────────────────────────────────────────────┘
        ↑ 以 projects/ 目录实现「项目级隔离」，框架 core/ 与项目解耦
```

分层规则（严格执行）：

| 层 | 职责 | 禁止事项 |
|---|---|---|
| 用例层 | 组合数据与业务调用，写断言 | 不直接裸调 httpx/驱动、不写接口 URL |
| 业务层 | 封装接口/页面操作为可读方法，挂 Allure 步骤 | 不写断言、不读配置 |
| 请求/驱动层 | 统一出口：Header、登录态、日志、截图 | 不写业务逻辑 |
| 配置/数据层 | 环境、账号、测试数据 | 不出现硬编码到代码中的 URL/账号 |

## 三、技术选型（含 APP / 小程序主流方案）

| 方向 | 选型 | 理由 |
|---|---|---|
| 接口 | pytest + httpx | httpx 支持连接池、超时控制、MockTransport（离线调试），API 与 requests 兼容心智 |
| Web UI | **Playwright（同步 API）** | 自动等待、多浏览器、录屏/截图、storage_state 复用登录态，当前 Web 自动化事实标准 |
| APP | **Appium 2.x（主方案）** | 企业中应用最广的成熟方案：Android(UiAutomator2) / iOS(XCUITest) 双端统一，原生/混合/H5 通吃，与 Selenium 语义一致，生态与 CI 集成最完善 |
| APP（备选） | Airtest / uiautomator2 | Airtest（网易，图像识别，适合游戏类）；uiautomator2（轻量，仅 Android）。均作为补充而非主方案 |
| 小程序 | **Minium（腾讯官方，主方案）** | 微信官方开源，可操作原生小程序组件、读取页面 data、调用 wx API，企业中小程序自动化最主流方案 |
| 小程序（备选） | 微信开发者工具 CLI + Playwright(Chrome DevTools 协议调试小程序 WebView)；纯 H5 页面可直接用 Playwright | 适合无原生组件诉求的 H5 型小程序 |
| 日志 | Loguru | 零配置结构化日志，按项目/环境分目录归档 |
| 报告 | Allure（allure-pytest） | 步骤/附件/环境信息/历史趋势 |
| 造数 | Faker（zh_CN） | 姓名/手机号/身份证等中文语境假数据 |
| 失败重试 | pytest-rerunfailures | `--reruns N`，区分「环境抖动」与「真实缺陷」 |

## 四、多项目隔离设计

- 每个被测项目独占 `projects/<项目>/` 目录：`config/`（环境+账号）、`api/`（业务层）、`data/`（测试数据）、`testcases/`（用例）；
- 框架 `core/` 只提供能力，不含任何项目信息；项目之间不互相 import；
- 用例通过 `from projects.project_a.api.user_api import UserApi` 显式引用本项目的业务层；
- **新项目接入 = 新增目录 + 配置 + 业务层 + 用例，框架代码零改动**；并提供脚手架生成器 `tools/create_project.py`，一条命令生成标准骨架，接入时间从 30 分钟缩短到 5 分钟（README 附接入清单）。

## 五、多环境设计

- `--env test|prod|<自定义>` 命令行切换，加载 `config/env_<env>.yaml`；
- 覆盖优先级：环境变量 `AUTOTEST_<KEY>`（如 `AUTOTEST_API_BASE_URL`）> YAML，满足 CI 敏感信息注入；
- 账号独立管理于 `accounts.yaml`，按 key 取用（default / admin / …），登录路径与 token 字段全部配置化；
- 正式环境仅跑 `@pytest.mark.smoke` 冒烟/巡检用例，CI 中按环境限制标记。

## 六、可复用公共资产清单

| 资产 | 实现位置 | 说明 |
|---|---|---|
| 请求层封装 | `core/http_client.py` | 公共 Header、Bearer 登录态注入、全链路日志、请求/响应自动附 Allure、耗时统计 |
| 登录态管理 | `core/auth_manager.py` | 账号级 token 缓存，会话内一次登录全程复用 |
| 统一断言 | `core/assertions.py` | 状态码 / JSON 路径 / 字段子集 / 文本包含，失败信息友好并附报告 |
| 日志 | `core/logger.py` | 控制台 + 文件双输出，按项目/环境分目录，10MB 滚动、保留 15 天 |
| 数据驱动 | `core/data_loader.py` | YAML 用例数据一键 parametrize |
| 失败重试 | pytest-rerunfailures | `--reruns 2 --reruns-delay 1` |
| 报告 | allure-pytest | `--alluredir=allure-results/<项目>`，报告按项目分目录 |
| 造数工厂 | Faker | 中文姓名/手机号/身份证/邮箱，动态数据防污染 |

## 七、各方向实施要点

### 7.1 接口自动化（MVP 已可运行）
用例 + 数据 + 业务层全部就绪；离线场景用 `httpx.MockTransport` 验证全链路，接真实环境只需把 `mock_api` 夹具换成 `http_client + AuthManager`。

### 7.2 Web UI（Playwright）
- POM：各项目 `ui/pages/` 继承 `core/ui/base_page.py`，只写定位与业务动作；
- 登录态复用：全局登录一次 → `storage_state` 保存 → 后续用例免登录；
- 失败增强：`pytest` hook 中失败自动截图 + 录屏（Playwright 内置 `video`）并附 Allure。

### 7.3 APP（Appium）
- `core/app/driver.py` 提供 Android(UiAutomator2) / iOS(XCUITest) 双工厂，caps 全配置化；
- POM 同 UI 层；设备农场后期接 STF / Sonic / 云真机；
- CI：Appium 服务随流水线容器启动，Android 用例跑模拟器。

### 7.4 微信小程序（Minium）
- `cli auto --project <路径> --auto-port 9420` 开启自动化端口，`core/miniprogram/driver.py` 工厂拉起；
- 可断言页面路径、组件属性、页面 data，甚至直接调用 wx API（`mini.callWxMethod`）；
- H5 型小程序可降级为 Playwright 方案，复用 UI 层全部能力。

## 八、CI/CD 集成（示例：GitLab CI）

```yaml
api-test:
  stage: test
  script:
    - pip install -r requirements.txt
    - python -m pytest projects/project_a --env test -m "api and not demo" --reruns 2 --alluredir=allure-results/project_a
  artifacts:
    when: always
    paths: [allure-results/, logs/]

ui-test:          # 需要 Docker 镜像内置 playwright + chromium
  script:
    - python -m pytest projects/project_a --env test -m ui --alluredir=allure-results/project_a
  allow_failure: true   # UI 用例初期允许失败不阻塞流水线
```

Jenkins 同理：示例文件已落地 `ci/Jenkinsfile`（声明式流水线 + Allure 插件 + 产物归档），命令同为 `pytest --env xxx -m <标记> --alluredir=...`。

## 九、落地路线图

| 阶段 | 内容 | 产出 |
|---|---|---|
| P0（本 MVP，已完成） | 框架分层 + 多项目/多环境 + 接口方向全链路 + UI/APP/小程序骨架 | 可运行的仓库 |
| P1（2-4 周） | 接入 1 个真实项目接口全量回归；CI 定时任务 + Allure 报告站；失败自动截图/录屏 hook | 每日回归报告 |
| P2（1-2 月） | UI 核心路径 20~30 条（storage_state 免登录）；APP 冒烟 10 条；小程序冒烟 | 四方向均有产出 |
| P3（持续） | 数据工厂增强、多线程分发、测试平台化（用例平台/报告聚合/资产看板） | 平台化 |

## 十、风险与约定

- 敏感信息（账号密码）一律走环境变量注入，仓库内只放占位；
- 正式环境用例必须可幂等（只读或可回滚），禁止破坏性操作；
- UI/APP 用例不追求覆盖率，只覆盖核心路径；接口层承担主要回归量；
- 所有用例强制打标记（api/ui/app/miniprogram/smoke/demo），便于 CI 按方向与环境调度。
