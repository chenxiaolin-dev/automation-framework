# 用例编写规范（YAML 用例引擎版）

> 目标：任何人打开用例 30 秒看懂「测什么、怎么测、为什么失败」。

## 一、用例文件约定

- 位置（引擎递归扫描两个根，见 `engines/api/case_loader.py` 的 `CASE_SCAN_ROOTS`）：
  - **`projects/<项目>/data/api/**/*_cases.yaml`（约定位置，新用例一律放这里）**
  - `projects/<项目>/api/cases/**/*_cases.yaml`（兼容保留，2026-10-01 起不再新增；
    该目录只放 pytest 入口 `test_yaml_cases.py` 与 `__init__.py`）
- 文件名必须以 `_cases.yaml` 结尾；同一份用例**不要在两个目录下各放一份**（会被收集两遍并触发「用例 ID 重复」）
- 入口统一为 `api/cases/test_yaml_cases.py`（固定内容，新项目由脚手架生成，不改）
- 项目三层包结构（`project_x/`、`project_x/api/`、`project_x/api/cases/`）必须有 `__init__.py`

## 二、文件结构

```yaml
meta:
  module: "收货地址"        # Allure Story 分组
  default_method: POST      # 文件级默认方法，用例可覆盖

variables:
  keyword: "固定值"          # 文件级变量，用例中 ${keyword} 引用

test_cases:
  - id: API_ADDRESS_ADD_001 # 全局唯一（脚手架/CR 时检查）
    title: "新增收货地址-正向"
    level: p0               # p0/p1/p2，自动映射 pytest marker
    tags: [smoke]           # 自动映射 pytest marker
    ...
```

## 三、变量四来源（`${...}`）

| 写法 | 来源 | 示例 |
|---|---|---|
| `${name}` | 文件级 variables / extract 提取 / 上下文 | `${address_id}` |
| `${ENV.KEY}` | 操作系统环境变量（未设置报错） | `${ENV.TEST_TOKEN}` |
| `${fake.xxx}` | Faker(zh_CN) 方法，支持拼接 | `"某路${fake.building_number}号"` |
| `${field}` | data_matrix 展开字段 | `${page}` |

变量值本身仍含 `${...}` 时**最多递归解析 3 层**（`engines/api/yaml_runner._resolve_token`），
所以可以先在 `variables` 里做一层别名再引用：

```yaml
variables:
  mobile: "${ENV.TEST_MOBILE}"     # 变量套变量，解析后是真手机号
test_cases:
  - request: {data: {mobile: "${mobile}"}}
```

## 四、执行流程与断言

执行顺序：**setup → 主请求 → validate → schema → extract → teardown**（setup/teardown 的 request 动作同样支持 validate/extract/schema）。

- 断言类型（20 种）：eq / ne / contains / not_contains / exists / not_empty / regex / in / gt / ge / lt / le / len_eq / len_gt / len_lt / type / is_true / is_false / exists / not_exists
- 检查路径：`status_code`、`headers.Content-Type`、`json`、`json.data.token`、`json.data.items[0].id`
- 注意：含 `[` `]` 的路径在 YAML 流式写法里必须加引号，否则解析报错 —— 写 `{check: "json.data[0].id", assert: exists}`，不要写 `{check: json.data[0].id, ...}`
- **异常用例断言从宽**：服务端参数校验可能缺失，写 `status_code lt 500` + `json.code exists`，禁止凭想象断言具体错误码
- 正向用例必须断言 `status_code eq 200` + `json.code eq 0`（业务码明确的服务）

## 五、数据与清理

- 正向造数用 `${fake.xxx}`（自动隔离），或 `core/data/isolation.unique_value`
- **产生脏数据的用例必须有 teardown 清理**（如新增后删除）
- 账号/密码等敏感信息走 `config/{env}.yaml` 的 auth 配置 + `${ENV.KEY}`，禁止写进用例文件
- 登录类参数不用手写：`conftest._export_auth_env` 会把 `api.auth.request.data` 的每个字段导出成
  `TEST_<字段名大写>` 环境变量（mobile → `TEST_MOBILE`、verifyCode → `TEST_VERIFYCODE`），
  用例里直接写 `${ENV.TEST_MOBILE}` 即可；CI 预设同名环境变量时优先用 CI 的
- 跨用例传值用 extract + depends_on，禁止用例内硬编码上游返回值

## 六、失败排查

1. 控制台 INFO（每步请求耗时/状态码）
2. `outputs/{project}/{env}/{type}/{run_id}/run.log`（全局 DEBUG）与 `cases/<用例>.log`（按用例隔离）
3. Allure 报告「失败归因」附件：失败用例自动挂载 run.log + case log + 最近 20 条 API 交互（已脱敏）
4. 疑似环境抖动：`--reruns 2` 复跑确认再定位

## 七、Code Review Checklist

- [ ] 用例 ID 全局唯一、命名带模块前缀
- [ ] level/tags 已标注（自动映射 marker，供 CI 调度）
- [ ] 异常用例断言从宽，正向用例断言到业务码
- [ ] 产生脏数据的用例有 teardown
- [ ] 敏感信息未出现在用例文件中
- [ ] 依赖链用 depends_on 而非靠执行顺序巧合
